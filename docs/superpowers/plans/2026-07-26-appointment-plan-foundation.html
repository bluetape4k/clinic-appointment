01 · Delivery Boundary

이번 배포는 “계획”까지만 만든다

IN

구매가 만든 미래 의무

catalog version, BOM, 반복 횟수, dependency, 고객 희망 일정, plan 상태, inbox/outbox를 저장하고 조회한다.

OUT

아직 방문을 만들지 않는다

AppointmentItem, allocation, hold, confirm, consent, refund, disruption, overbooking과 broker publish/ack는 후속 slice다.

순서 보정: 예약 확정은 typed policy snapshot을 요구한다. 따라서 plan foundation 다음에 policy foundation을 먼저 구현하고, 그 뒤 visit/commitment로 간다.

03 · Execution Order

7개 task, 매 단계 RED → GREEN → commit

  1. 계약 고정
    catalog·plan value model, bounded validator, deterministic hasher를 순수 Kotlin으로 만든다.
  2. aggregate 저장
    catalog 3개 테이블과 plan 3개 테이블, repository, mapper를 multi-dialect test로 고정한다.
  3. V8 schema parity
    core 6개 테이블과 inbox/outbox/quarantine/audit를 H2·PostgreSQL·MySQL에 additive migration한다.
  4. catalog sync API
    tenant·clinic·source authority가 포함된 identity 아래 CREATED, UNCHANGED, STALE_IGNORED, conflict 계약을 제공한다.
  5. purchase event 수렴
    OFF/SHADOW/WRITE gate 아래 inbox + plan + outbox를 한 transaction에서 처리하고, 실패 event는 별도 암호화 quarantine과 append-only audit로 보존한다.
  6. plan read API
    clinic operator가 tenant/clinic 범위 안에서 상품 근거, 희망 일정, treatment DAG를 조회한다.
  7. 문서·회귀·리뷰
    README parity, migration matrix, module regression, 보안·안정성 review를 수렴한다.

07 · Stop Condition

여기까지 증명되면 첫 slice가 끝난다

authority-qualified 한 구매는 하나의 plan과 결정적인 treatment DAG를 만들고, catalog·event 재전송은 중복을 만들지 않으며, tenant/clinic 경계를 넘지 않는다. 세 DB migration과 PostgreSQL/MySQL 성능·EXPLAIN 증거가 통과하고 기존 appointment API가 그대로 동작해야 한다. outbox enqueue는 delivery 완료로 표시하지 않으며 transport가 연결되기 전 production WRITE는 비활성이다.

완료 증거

targeted RED/GREEN, migration matrix, performance·EXPLAIN, shadow diff, quarantine/redrive·rollback, HTML smoke, module tests/build, 7-Tier P0=0/P1=0.
