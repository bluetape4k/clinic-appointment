# 한국어 기술문서 전환에서 보존 경계를 먼저 고정하기

## 배경

`clinic-appointment`는 한국어 사용자만을 위한 예제 저장소이므로 사용자 대상
문서와 사람이 작성한 GitHub 기록을 한국어 기술문체로 통일했다. 문서의 언어를
바꾸는 작업이지만 README의 locale 자산, 코드 예시, 운영 명령, 이슈·PR의 추적
정보가 함께 얽혀 있어 단순한 문자열 치환으로 처리하지 않았다.

## 적용한 원칙

1. `AGENTS.md`와 `CLAUDE.md`는 LLM-facing 운영 계약이므로 영어를 유지했다.
2. 코드, 명령, API 이름, 식별자, URL, SHA, 이슈/PR 번호, 정확한 오류 문구는
   그대로 보존하고 주변 설명만 한국어로 작성했다.
3. README와 도식·차트는 한국어 locale 파일을 사용하되, 영어·한국어 시각
   자산이 함께 배포되는 기존 파일명과 manifest 계약은 변경하지 않았다.
4. 사람이 작성한 Issue와 PR만 번역했다. Dependabot이 생성한 PR 50개는 자동
   생성 메타데이터를 보존하기 위해 번역 대상에서 제외했다.
5. 원문 증거가 필요한 역사 문서는 한국어 요약을 앞에 두고 원문·기술값을
   보존해 추적 가능성을 유지했다.

## 검증 교훈

- Markdown의 fenced code block과 링크 대상은 번역 전후 개수와 기술값을 대조해야
  한다. 링크 label을 번역해도 target 경로와 locale suffix는 실제 파일을 가리켜야 한다.
- Kotlin KDoc과 reader-facing `//` 주석은 실행 코드와 분리해 diff를 검사하면
  문서 변경에서 동작 변경이 섞이지 않았음을 빠르게 증명할 수 있다.
- GitHub 기록은 로컬 파일만으로 완료를 주장할 수 없다. `gh`로 제목·본문·작성자·
  상태를 다시 조회하고, PR 본문의 마지막 섹션이 `## DoD Status`인지 확인해야 한다.
- 전체 빌드보다 변경 범위에 맞는 모듈 컴파일을 먼저 실행하고, CI가 제공하는
  저장소 전체 검증은 PR 단계에서 별도로 확인한다.

## 후속 규칙

새 사용자 문서, KDoc, Issue, 사람이 작성한 PR을 추가할 때도 이 경계를 적용한다.
자동 생성 산출물이나 운영 계약 파일을 번역 대상으로 확장하려면 별도의 합의와
검증 계획을 먼저 기록한다.
