# #451 응답 스트림 소유권과 실패 경로 검증

## 원인과 결정

`JdkSchemaRegistryCompatibilityReader`는 비성공 상태에서 `use`에 진입하기 전에
예외를 던졌다. 정상 응답의 정리만으로 전체 응답의 자원 수명이 보장되지 않았다.
상태 검사를 `response.body().use` 안으로 옮겨 비성공 본문도 읽지 않고 닫는다.
닫기도 실패하면 도메인 예외를 유지하고 닫기 예외를 suppressed로 보존한다.

공통 bounded HTTP API 전환은 `bluetape4k-projects#1643`에 의존한다.
이번 변경은 #451의 누수 수정 단계이며, 이슈 전체 완료로 처리하지 않는다.

## 검증

- 수정 전 새 테스트 12개 중 4개 실패: 401·403·500에서 close 횟수 0,
  비성공 응답의 suppressed close 예외 누락.
- 수정 후 새 테스트와 기존 Schema Registry 테스트 18개 통과.
- `:appointment-messaging:test`: 147개 통과. 정상·빈 응답, 64 KiB 경계,
  읽기 실패, 닫기 실패와 예외 우선순위를 검증했다.
- Gradle Detekt는 Kotlin 2.4.10/2.4.0 불일치로 대상 소스 분석에 실패했다.
  별도 Detekt 1.23.8 비교에서는 변경 전후 기존 경고 7건이 동일했고 새 경고는 없었다.
  이 비교는 저장소 Detekt 버전의 성공 증거를 대신하지 않는다.

## 다음 작업의 예방 규칙

- HTTP 스트림을 반환받으면 상태 검사·파싱보다 먼저 정리 범위에 넣는다.
  성공뿐 아니라 비성공·읽기 실패·닫기 실패에서 close 횟수와 예외 우선순위를 검사한다.
- 백그라운드 도구의 시간 초과를 프로세스 종료로 해석하지 않는다. 이번 작업은
  실행 상태 확인 없이 재실행해 중복 Gradle 실행과 증분 캐시 오류를 유발했다.
  재실행 전 기존 프로세스를 확인하고, 동일 worktree의 빌드는 하나씩 실행한다.
- 존재하지 않는 모듈 Detekt 작업이나 루트 NO-SOURCE 결과를 검증으로 세지 않는다.
  작업 등록과 실제 분석 대상 파일을 먼저 확인한다.
- 이미 읽은 지침은 재사용하고 변경 여부가 판단에 영향을 줄 때만 다시 확인한다.
  이번 작업에서 반복적인 지침 확인과 실행 실수로 사용자의 피드백을 받았다.
  다음에는 재현·수정·검증 증거를 먼저 확보하고 진행 상황을 짧게 보고한다.
